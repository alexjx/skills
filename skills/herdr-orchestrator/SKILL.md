# Herdr orchestrator

Keep a coordinator responsible for interacting with the user and coordinating the other agents. Roles are responsibilities, not required separate sessions. Confirm their owners and workflow before dispatching work.

Before discovering agents or issuing control commands, resolve the runtime using [backend selection](references/backend-selection.md). `herdr-core` (`hc`) and legacy `herdr` (TUI) are incompatible runtimes, not alternative command spellings. Load only the selected official skill for operations. Use it for terminal addressing, startup readiness, direct messaging, and recovery. If its required skill, CLI, session context, or downstream messaging capability is unavailable, surface that setup blocker before starting the job; never fall back to the other runtime.

## Agree on the team and workflow

On the first run for a job, inspect available agents and existing user instructions. Use agent names and stated context to propose responsibilities; names are hints, not authorization. Present one concise proposal for the user to confirm or correct before starting agents or dispatching work:

- **Coordinator:** user interaction, routing, dependency tracking, blockers, and final delivery.
- **Planner:** scope, decomposition, dependencies, and acceptance criteria. If absent, the coordinator performs these duties.
- **Designer:** personally produce the detailed technical design, including data flow, interfaces, and implementation decisions. Never delegate this responsibility to other agents. If there is no separate designer, confirm an existing agent as the design owner before implementation.
- **Reviewer:** evaluate outputs against the agreed criteria and request corrections or approve. If absent, the coordinator performs these duties; review is not skipped.
- **Workers:** one or more agents executing explicitly assigned scopes. Ask the user to choose or confirm each worker's responsibility, using names to suggest likely scopes when helpful. Do not silently assign specialties, divide work, or create extra workers.

Include each agent's name/address, role(s), scope, and expected output. Confirm the workflow alongside the role map: stages, dependencies, who hands off to whom, the evidence and conditions required for each transition, correction routes, escalation conditions, and final acceptance checks. Explain that this initial confirmation establishes responsibilities and handoff rules. Existing explicit choices count as confirmation; ask only about unresolved choices. While awaiting confirmation, discovery and proposal preparation may continue, but dependent execution must wait.

For coding jobs, propose the existing implementation → review → integration workflow as the **default**, not a requirement. It provides a clear quality gate on each exact candidate and a single owner for combining concurrent changes and checking the final result. Planning precedes implementation; review findings reach the worker through the dispatcher; blockers and final results go to the coordinator. Integration is a responsibility the coordinator covers unless the user confirms another owner, not a required extra agent. Adapt the stages and evidence to other tasks or the user's preferred workflow.

Record the confirmed agreement inline for simple jobs or in `.agents/plans/<job-id>.md` when it needs to survive sessions. On resume, reuse it and reconcile messages, checkpoints, and current artifacts before replaying work. Confirm material changes to responsibilities or handoff rules rather than repeating the whole setup.

## Run the agreed job

1. Read [handoff guidance](references/job-schema.md) and [role prompts](references/worker-prompts.md). Bind logical roles to the confirmed agents, including coordinator fallbacks. Use separate writable worktrees only when multiple agents work concurrently. With a single active agent, use the existing workspace, including when that agent performs multiple roles in sequence.
2. Start and confirm receivers are ready before sending initial work. Send each agent its confirmed scope, criteria, workspace, expected messages, and dispatcher address inline. Include a stable sender identity in each dispatched task and require it in every reply, including subagent replies. Use the identity available from context; otherwise the orchestrator assigns a unique ID and records its mapping to the agent and runtime address. Tell idle agents to return to their prompt after setup, then kick off dependency-free items once the designer has completed any required technical design.
3. Workers send results, evidence, blockers, and decision requests only to their assigned orchestrator/planner dispatcher. Workers must never message another worker or themselves, even when a worker also holds reviewer, designer, integrator, or Administrator duties. Workers must not dispatch subagents; request any additional work through the dispatcher. The dispatcher routes actionable assignments to the next owner when handoff conditions are met. Before every send, compare verified sender and recipient identities and runtime addresses; never send to yourself. Default to concise plain text, without JSON envelopes or handoff files. Use files for complex content, large artifacts, or necessary recovery checkpoints, with the actionable summary still inline. If consecutive roles belong to the same agent, perform the next responsibility locally and record its outcome instead of messaging itself.
4. Every dispatched agent or system must send a completion response to its dispatcher when its assigned task finishes. Combine the result handoff and completion report when they concern the same outcome. Include its Agent ID, job/item, result, evidence, and a request for the Administrator to check pending jobs from the user's requests. The coordinator acts as Administrator unless another owner is confirmed. The dispatcher forwards pending-job queries to that owner; workers never contact another worker to perform this check. The Administrator reconciles completed, pending, blocked, and newly unblocked work against the user's requests, then dispatches eligible work under the confirmed agreement or reports blockers. When the same agent owns these roles, perform and record this check locally.
5. The coordinator tracks dependencies and communicates with the user. The confirmed integration/completion owner combines accepted outputs and performs final verification, then reports to the coordinator for user delivery. Before final delivery, the Administrator checks that no requested work remains unaccounted for. Keep publishing and merging subject to the user's authorization.

For the default coding workflow, see [the worked example](references/example-job.md). Use a replacement worker only after resolving ownership of the prior worker's write access and confirming changed responsibilities.

Keep routine status traffic silent. Workers must not send `reply`, `acknowledge`, or receipt/readiness messages when receiving an assignment, a working/busy status, or an informational update. Begin assigned work or update local state without messaging the planner or orchestrator. Check startup readiness through the selected runtime's inspection mechanism. Send only actionable results, required completion reports, blockers, or decision requests; receiving a status message is not task completion and must not trigger a completion report or pending-job query.

This rule is bidirectional: the orchestrator and planner must never send acknowledgement or acceptance statuses to workers, including after completion reports or pending-job queries. Record accepted results internally and remain silent toward the reporting worker. If corrections are required, dispatch a concrete correction assignment with findings and acceptance criteria; otherwise send only the next eligible assignment when there is one. Do not send `ACK`, `ACCEPTED`, `received`, `no pending jobs`, or equivalent status-only messages to workers. Review approval goes to the dispatcher, which assigns integration as actionable work; never send it back to the implementer as an acceptance notice.

Continue execution and review until the acceptance criteria pass while meaningful progress is being made; do not impose a default round limit. Use the [progress and repetition rules](references/job-schema.md#progress-and-repetition) to detect stalled or cycling work, change approach, and escalate when a decision is needed.
